从工具循环到 Code Mode

Pi 架构演进：v0.9.4、v0.99.2 与 v1.3.0

一部跟着源码读的中文电子书。 本版依据官方仓库、固定版本源码和发布记录整理，核查日期为 2026 年 10 月 20 日。核查时最新的 GitHub 正式发布为 v1.3.0，发布时间为 2026 年 10 月 15 日。本书解释这个版本快照，不把以后 main 上的代码混进来。

先说结论：Pi 的核心仍然是“模型产生响应，工具执行操作，结果供下一轮模型使用”的循环。变化主要发生在循环外围：树形会话、统一扩展系统、更丰富的工具契约、内置 MCP，以及让模型用 JavaScript 编排工具的 Code Mode。最新仓库还提供独立的实验性 Durable 运行时，它可以恢复中断任务，但不是普通 CLI 已经切换过去的新内核。

本书沿用同目录学习课程的组织方式：一章解决一个问题，先建立直觉，再看图、沿源码追踪，最后做例子和练习。重点了解 Code Mode，可以先读第 1、3、5、6、8、11 章；想理解整套架构则顺序阅读。你只需了解基本 JavaScript、Promise，以及“模型能够请求调用工具”这一概念，不需要预先掌握编译器或 WebAssembly。

第 1 章：先把版本说清楚

本章目标：知道我们究竟在比较哪两个时代。

0.9.x 和 0.99.x 不是同一组版本。版本号不是小数，而是整数元组；次版本号 99 在 9 之后。把两者混为一谈，就会把早已存在的能力误写成最新版本才出现。

参照点 日期及依据 为什么重要
v0.9.4 2025-11-26，标签对应提交 可用的最后一个 0.9.x 标签；传输抽象、早期工具循环、线性会话文件
v0.31.0 2026-01-02，变更日志 单文件内的树形会话与原地分支
v0.35.0 2026-01-05，变更日志 hooks 与自定义工具统一成 extensions
v0.99.0 2026-09-29，变更日志 内置 Code Mode、工具搜索、MCP 与嵌套工具契约
v0.99.2 2026-09-30，变更日志 MCP 按需发现，减少启动等待和工具描述变化
v1.0.0 2026-10-01，变更日志 更精简的 Code Mode 提示、图像生成、默认全屏 TUI
v1.3.0 2026-10-15，正式发布 本书最新端点；取消与 worker 数量控制、恢复活动工具集等修复

官方仓库现在叫 earendil-works/pi，历史上的 badlogic/pi-mono Git 地址仍能访问到这个项目。旧源码里的包名前缀是 @mariozechner/*，当前是 @earendil-works/*。改名是迁移时必须处理的事情，但改名本身不是一种新 Agent 算法。S1、S2

你原有的 learning/pi-mono 检出点显示为 v0.54.0-1-g3a3e37d3，而且存在本地修改。本次没有修改它，也没有升级当前安装的 Pi。新的 sources/ 目录单独保存了三个用于比较的固定版本。

本书说的“架构”包括什么

我们比较模块职责、依赖边界、数据流、状态归属、扩展方式和失败行为，而不是逐条复述所有模型新增、终端按键修复。完整的文件级变更清单另存于 sources/，适合需要穷尽排查时查阅。

书中区分三类内容：

  • 已核实行为：固定标签的文档、源码或发布记录能够支持。
  • 教学模型：为了讲清职责而简化的图和伪代码。
  • 示意算术：用于解释开销的假设工作量，不是实测性能。

不要被 diff 数字带偏

完整 Git 比较中，v0.9.4 到 v1.3.0 涉及 2,110 个变更文件；v0.99.2 到 v1.3.0 涉及 1,315 个。里面包括测试、文档、生成数据和实验代码删除。尤其 v1.2.0 删除了尚未进入正式发布包的实验性服务端、客户端和插件栈。不能看到大量删除，就断言正式 CLI 已经换成另一个分布式运行时。S2、S18

理解检查： 如果你以前用的是 v0.99.2，Code Mode 不是 v1.0 才发明的；如果你指的是 v0.9.4，就必须把中间接近一年的 harness 演进算进去。

左边是旧版职责位置，右边是新版普通 CLI 的对应层。这里强调代码归属与装配边界，不表示所有能力都是在单个版本中同时完成迁移。

第 2 章：v0.9.4 原本是怎样工作的

本章目标：先看清旧循环，再理解新增的编排层。

v0.9.4 已经把模型提供商接入、有状态 Agent、编码应用和终端渲染拆开。它并不是“一段 shell 加一次模型调用”。

一个容易忽略的细节：真正的循环在 packages/ai/src/agent/agent-loop.ts。有状态 Agent 在 packages/agent/src/agent.ts，接收 AgentTransport，通过 transport.run(...) 遍历事件。编码应用负责把这些模块装配起来。S3、S4

跟着一次请求走

假设你说：“读 package.json，告诉我包名。”

Agent 构造用户消息，把应用消息转换成模型能理解的消息，再交给 transport。循环接收模型流式响应。如果响应中包含 read 调用，就按名称查找工具、校验参数、执行 execute()，把结果变成 toolResult 加入上下文，再请求模型给出答案。

下面是教学伪代码，不是逐字摘录：

while (hasToolCalls || queuedMessages.length > 0) {
  injectQueuedMessages();
  const assistant = await streamModel(context);
  for (const call of assistant.toolCalls) {
    const args = validate(call);
    const result = await findTool(call.name).execute(call.id, args, signal);
    context.messages.push(toToolResult(call, result));
  }
}

这里有两个历史事实。第一，工具参数校验早就存在，不能把它算作 Code Mode 才带来的能力。第二，旧循环通过带 await 的 for...of 逐个执行工具；当前 Agent 支持同一响应中的多个调用并行执行。S4、S6

状态分别放在哪里

Agent 维护消息、当前模型、流式状态、待执行调用 ID 和消息队列。消息转换器负责把附件等应用数据变成模型输入。事件流让 UI 观察 message_start、message_update、message_end、工具执行和回合边界。

旧 SessionManager 使用 JSONL，保存会话头、消息、模型变更和思考等级变更。条目没有当前的 id / parentId 树形链接。createBranchedSession() 会新建文件，把分支点之前的消息复制过去。因此旧版不是没有分支，而是“复制历史到新文件”，不同于当前在一个文件中切换树形分支。S5

那时还没有什么

该标签没有当前这一套内置 Code Mode、MCP、tool search 组合，也没有后来统一的扩展系统。仓库还包含 mom、web-ui、pods、proxy 等应用或配套模块。说明多界面复用从早期就重要，但不意味着这些目录现在仍原封不动地存在。

练习： Anthropic 流式事件归一化应该放哪里？模型接入层。重画终端一行放哪里？TUI。判断是否继续下一轮模型请求放哪里？Agent 循环。文件位置虽变，职责判断仍然有效。

第 3 章：当前架构，分清 CLI 与独立基础库

本章目标：看到整张地图，但不把相邻模块当作同一条执行链。

v1.3.0 的 CLI 仍建立在有状态 Agent 上，不过循环已经和 Agent 放到一起：packages/agent/src/agent-loop.ts。编码应用层提供 AgentSession、会话持久化、上下文投影、资源加载、扩展、模型运行时和不同交互接口。S6、S7

这张图是职责图，不是完整 npm 依赖图。Code Mode 和 MCP 通过 CLI 的内置扩展接入，没有替换 Agent 或模型接入层。

用三个边界理解后面的所有章节

推理边界： 模型决定目标、调用和代码；Code Mode 中的常规循环、条件、聚合由 JavaScript 执行，不必每个中间结果都重新问模型。

上下文边界： harness 决定下一次模型请求看到什么。磁盘历史、UI 展示、嵌套调用记录和模型上下文不是同一份东西。

能力边界： 脚本只能调用注入的能力，但注入的 shell 工具可能拥有 Pi 进程的全部权限。JavaScript 沙箱不等于 shell 的文件系统沙箱。

后面的章节沿着这三个边界展开。它们比记忆一串类名更能解释设计为什么这样变化。

第 4 章：一次请求的完整生命周期

本章目标：区分消息流、持久历史和模型输入。

理解新版最有效的路线不是先读所有类，而是跟一条请求走到底。

  1. CLI、SDK 或 RPC 收到输入。提示模板可先展开，扩展可以处理命令或变换输入。
  2. AgentSession 负责运行准备、模型与工具配置、压缩检查、扩展生命周期和队列。
  3. SessionManager 从当前叶子追溯活动分支，重建已定稿的上下文。
  4. harness 组合系统提示、分支消息、工具声明和模型设置，交给 provider。
  5. provider 产生流式事件，Agent 归一化为消息和回合事件。
  6. 如果 assistant 请求工具，则校验、触发扩展钩子、执行，记录结果。
  7. 如果还有工具结果或队列需要处理，则继续；否则进入最终收尾。

图中省略流式 token 与多轮重试，保留了最重要的边界：嵌套工具结果先回给脚本，而不是直接变成下一次模型输入。 S7、S9、S10

同一响应的并行，不等于 Code Mode

当前 Agent 的工具执行默认支持并行：先顺序做调用前检查，再并行执行被允许的工具；完成事件按实际完成顺序发出，最终工具结果消息仍按 assistant 源码中的调用顺序落入历史。需要共享状态的工具可使用顺序执行方式。S6

这意味着：模型在一个响应里同时请求三次 read，不使用 Code Mode 也可能并行。Code Mode 多出的价值是在一个脚本中表达依赖、分支、过滤与聚合，并控制哪些结果跨回模型边界，而不只是“把串行变成并行”。

三种历史不要混淆

视角 保存或展示什么 用途
原始会话历史 消息、分支、压缩、上下文编辑、配置变化、自定义状态等 追溯、恢复、导出
UI 和执行事件 流式输出、嵌套工具进度、完成时长等 观察正在发生什么
模型上下文投影 活动分支经过压缩、上下文编辑、消息转换后的输入 下一轮模型推理

当前 JSONL 条目通过 id / parentId 组成树。/tree 可以从旧节点继续，同时保留被放弃分支。压缩追加摘要和保留边界，而不是删除原始历史；context_edit 可以让某个历史条目在未来模型上下文中被省略或替换，但不重写其原始记录。S11

压缩和 Code Mode 各解决什么

默认压缩阈值的概念是：

contextTokens > contextWindow - reserveTokens

Code Mode 是在信息进入模型之前做减量；压缩是在上下文已经积累后，把早期内容总结成摘要。前者不能替代后者。普通工具调用也可以先截断输出；Code Mode 更适合按数据含义做结构化筛选。S12

例如运行测试得到很长日志。工具截断保留头尾，不知道你只关心三个失败断言；脚本可从结构化结果中选出失败项，再让模型理解原因。但如果你把全部日志 text() 出去，就没有获得这部分上下文收益。

什么时候才算真的结束

SDK 的 agent_end 只代表一次底层 Agent 运行结束，随后还可能发生自动恢复、重试或排队工作。集成程序要确认 Pi 不再自动继续，应关注 agent_settled。把两者当成同一个事件，会导致 UI 过早解除忙碌状态或脚本过早退出。S9

理解检查： 从树中切回旧节点，会不会回滚已经写入的文件？不会。会话分支描述对话历史，不是文件系统快照。

第 5 章：Code Mode 到底改变了什么

本章目标：能用一句话解释它，并知道何时不该使用。

一句话：让模型写一段调用工具的 JavaScript，常规编排在脚本中完成，只把主动输出的内容交还模型。

普通工具模式下，工具编排分散在 assistant 的工具请求及其后续模型响应中。Code Mode 把部分编排移到程序执行侧，模型看到一个外层 codemode 调用，脚本内部可以调用很多工具。底层工具仍然是真实工具。S10

一个具体任务：检查三个 package.json

需求：“读取根目录、api 和 web 的 package.json，只告诉我包名与 scripts 里有没有 test。”

不用 Code Mode，模型可以请求三次 read，收下三个完整文件，再挑选字段。它也可以请求 shell 直接聚合，或调用专门工具。Code Mode 不是唯一能做聚合的办法。

使用 Code Mode，可以表达为：

const paths = [
  "package.json",
  "packages/api/package.json",
  "packages/web/package.json",
];

const rows = await Promise.all(paths.map(async (path) => {
  const raw = await tools.read({ path });
  const pkg = JSON.parse(raw);
  return { path, name: pkg.name, hasTest: Boolean(pkg.scripts?.test) };
}));
text(rows);

假设三个文件都是未截断的有效 JSON，脚本内部会拿到全部内容，模型只收到选出的字段。read 返回的是字符串，不应写成 raw.output。如果读的是超大文件，被工具截断后就可能不是有效 JSON；应换成专门读取并解析的工具，或通过受控 shell 生成少量结构化数据。Code Mode 不会自动修复上游工具截断。

把控制流也写进去

如果其中一个包不存在，上一段的 Promise.all() 会让整个表达式失败。读取多个独立来源时，更实用的版本是：

const paths = ["package.json", "missing/package.json"];
const results = await Promise.allSettled(
  paths.map(async (path) => JSON.parse(await tools.read({ path })))
);
text(results.map((r, i) => r.status === "fulfilled"
  ? { path: paths[i], name: r.value.name }
  : { path: paths[i], error: String(r.reason) }
));

Promise.allSettled() 让失败和成功一起交给后续逻辑。它不是“忽略错误”，而是把错误变成你必须检查的数据。并发的调用必须互不依赖；不能把“写文件”和“马上读取刚写的文件”随意放在同一个并发数组里。

上下文收益怎么估算

下面只是示意，不是 Pi 性能测试。设有 N 个独立调用，每个原始结果 R 个字符，最终每项只需要 S 个字符。

全部原样返回：约 N × R
脚本选择字段：约 N × S + 外层包装

若 N = 12、R = 20,000、S = 300，数据量从约 240,000 个字符变成约 3,600 个字符，再加脚本和结果包装。字符不是 token，也不是费用；实际还受工具定义、模型分词、缓存和输出限制影响。这个例子只说明“把不需要的数据留在执行侧”的价值。

哪些事不值得套一层脚本

只读一个短文件，直接 read 通常更简单；要跑整个项目测试，直接 bash 就可能够了；需要长时间重型计算，QuickJS 也不比专门程序合适。不要为了使用 Code Mode，把本来一行能讲清的请求改成难读程序。

小结： 它的核心不是模型会写代码，也不是并行本身，而是把“工具输出到模型上下文”之间增加了一个可编程的数据处理层。

动手调一调：多少信息需要跨回模型？

修改调用数量与结果大小，观察字段筛选前后的字符量。这里只算数据字符，不估算 token、费用或实际耗时。

240,000 字符 → 3,600 字符

假设每项只返回 300 字符，忽略脚本与外层包装。工具本身可能已有截断；这不是实测速度对比。

第 6 章：拆开沙箱，看见真正的调用链

本章目标：知道脚本在哪里运行，权限检查在哪里发生。

普通 CLI 的 Code Mode 由两层组成：packages/codemode 提供通用沙箱；coding-agent/src/extensions/codemode 负责把它接到 Pi 的工具、会话、展示和模型运行时。前者没有 Pi 内部包依赖，因此也能脱离编码代理单独使用。S13

从源码追一次 tools.read()

  1. tool.ts 定义 codemode 工具、输入形式和模型可见说明。
  2. executor 读取当前可调用工具 ctx.tools，把每个工具包装成沙箱能力。
  3. 创建 CodemodeSandbox，设置 QuickJS WASM、worker 入口、内存限制和 worker 准入控制。
  4. execute() 启动 worker，在独立 WASM 实例中创建新的 QuickJS VM。
  5. VM 内的 prelude 暴露 tools、text、image、console、store / load 等接口，桥接函数藏在闭包中。
  6. 脚本调用 tools.read(...)，消息经过 worker 桥返回主线程。
  7. 主线程调用 ctx.executeTool()，进入参数校验及 tool_call / tool_result 钩子。
  8. 结果被转换成脚本值，返回 VM；脚本选择性输出。
  9. executor 关闭沙箱、处理状态写入、截断输出、保存图片、生成外层工具结果。

在 v1.3.0 的 execute.ts 中，关键语句是：

const outcome = await ctx.executeTool(tool.name, args, { signal: callSignal });

它解释了为什么“脚本里的工具调用”不是偷偷绕过工具链直接执行函数。已有扩展实现的拦截与权限确认仍可以生效。不过 Pi 没有默认对每次调用逐一确认的内置权限系统；这里说的是扩展钩子可以执行权限策略，不是默认已经有一层强制审批。S14、S15、S25

为什么不用 Node 的 eval

脚本里没有 Node API、文件系统、网络、模块加载和定时器。不能直接使用 process、require、fetch 或 setTimeout，需要访问外部世界就通过注入工具。eval / Function 即使存在，也只能在同一个 VM 里生成更多代码，不凭空获得宿主能力。

QuickJS 是解释器，编译为 WebAssembly 后运行在 worker。worker 避免一段同步死循环卡住 Pi 主线程；WASM 实例分离 VM 内存；能力注入限制脚本可以接触的接口。这是分层设计，不是一句“用了沙箱所以绝对安全”。

限制属于哪一层

层次 典型限制或职责
脚本源格式 第一行可选 // @options:；错误位置或非法字段会报错
VM CLI 每脚本 256 MiB 堆限制，无法分配时失败
宿主/worker deadline、abort、worker 生命周期与数量限制
输出收集 16 Mi 字符及 100,000 个输出项目上限
模型结果格式化 默认约 10,000 输出 token 预算，超长保留头尾并保存完整文本
底层工具 参数、外部进程、远程调用、工具自身截断与超时
操作系统或容器 文件、进程、网络与凭据的真正权限边界

不要混用这些限额。256 MiB 是 CLI 集成选择，不是所有独立沙箱部署的通用默认；Cloudflare 默认限制又不同。外层输出 token 预算也不是 VM 内存限制。S10、S13

一个危险的误解

await tools.bash({ command: "某个有破坏性的命令" });

命令执行在工具能力背后，能接触什么取决于 Pi 进程或工具专属容器，不取决于 QuickJS 是否能直接读文件。需要强隔离时，限制容器挂载、网络、账户和凭据；只限制 JavaScript 全局变量远远不够。

源码阅读顺序： tool.ts → execute.ts → codemode/src/runtime/host.ts → worker.ts → vm.ts → prelude-source.ts。先沿着一次调用走通，再研究声明生成和模型辅助接口。

第 7 章：工具太多时，怎样发现而不塞满提示

本章目标：分清“注册”“向模型声明”和“可被脚本调用”。

过去常见的思路是：把所有工具的名称、说明、参数 schema 放进模型请求。工具很少时直观；几十个服务、几百个工具时，就会扩大提示、干扰选择，还容易让工具集变化影响缓存。

当前 Pi 把几件事拆开：工具可以已注册，却不直接声明给模型；可以供脚本调用，却不在 Code Mode 说明里列出；也可以按需搜索后再声明。不可见不等于不可用，不可见更不等于已撤销权限。 S16、S17

MCP 的四种 exposure

MCP exposure 默认向模型声明？ 脚本可调用？ 常见用途
direct 是，受当前工具选择约束 是 少量高频工具
codemode 否，默认也不列入 Code Mode 描述 是 大多数服务，先发现再组合
deferred 否；tool_search 可加载声明 是 希望发现后按普通工具直接调用
hidden 否 否 保留注册信息但使其不可达

MCP 默认使用 codemode。普通扩展工具还有 model-only，适合仅让模型直接调用、禁止其他工具间接调用的编排器或问答工具。不要把 MCP 配置表和扩展底层表机械合并：MCP 集成会处理命名空间和延迟发现，最终可达性还取决于禁用、过滤与活动集合。S15、S16

四个发现入口，各做一件事

const hits = await searchTools("search documentation", { limit: 3 });
text(hits);
  • ALL_TOOLS：当前可调用目录，包含名称和说明。
  • searchTools(query, options)：BM25 相关性排序，找候选。
  • describeTool(name)：获得某个工具的说明与 TypeScript 声明。
  • describeNamespace(name)：读某个命名空间的指令和工具信息。

三个查询 helper 都是异步接口，必须 await。BM25 是文本检索，不是理解整个业务的语义代理；搜索词和工具说明的质量会影响结果。发现后应确认参数，不能猜一个名字就调用。S10

示意流程如下，其中 hits[0] 只是候选，必须读完说明再决定是否合适：

const hits = await searchTools("read documentation page", { limit: 3 });
if (hits.length === 0) return "没有找到候选工具";
text(await describeTool(hits[0].name));

发现信息会作为这一轮结果交还模型，下一轮可据此编写准确调用。不是所有发现都必须和执行挤在一个脚本里。

codemode.mode 的 on 与 only

on 是默认：已声明工具继续直接可见，并附带脚本调用提示。only 会隐藏那些底层工具的直接声明，将调用入口集中到 Code Mode；可调用集合本身不会因为“隐藏声明”自动消失。

{
  "defaultTools": ["+codemode"],
  "codemode": { "mode": "on", "inlineBudget": 3000 }
}

inlineBudget 是声明文本的估计 token 预算，约按字符数除以四估算，不是精确分词结果。超过预算的工具由发现接口寻找。当前默认 MCP 工具本来就不逐个写进 Code Mode 描述。only 是呈现和编排策略，不是更强的 OS 沙箱。S17

为什么 MCP 不阻塞每次启动

v0.99.2 开始，非 direct 服务器不再阻塞首个 prompt，先在后台连接。到脚本点名某个服务器，或搜索全部工具时，再等待相关连接。当前通过 reachesTools(input) 描述编排器可能触及哪些工具或命名空间；MCP 扩展据此等候必要服务器。搜索目录意味着可能触及全部工具，所以要等待更多服务。S2、S15、S16

这也是 v1.2.0 将 MCP 与 Code Mode 解耦的重要意义：不是 MCP 到处硬编码“识别某个内置实现”，而是利用通用工具契约识别编排器的可达范围。替换同名编排工具时，需要提供相应 reachesTools 契约。

一个容易造成权限误判的 CLI 细节

pi --tools read,codemode

在当前版，这不会自动删除 MCP 工具；它们仍可能被脚本调用。要去掉 MCP，可以用 --no-mcp；按 MCP 名称筛选时，使用 mcp__ 模式；排除工具则用 --exclude-tools。不要把 allowlist 的表面阅读当成完整权限审计。S16、S19

第 8 章：结果、失败、并发与状态

本章目标：写出在真实失败中仍然可理解的脚本。

Code Mode 最容易写错的不是语法，而是返回值和失败契约。不要假定“所有调用都返回字符串”，也不要假定“失败都会 throw”。

三种常见结果

工具 脚本通常拿到什么 需要检查什么
read 读文本 字符串 是否被截断，是否符合预期格式
bash { output, exit_code, truncated, full_output_path?, ... } exit_code，即使 Promise fulfilled 也可能执行失败
MCP 工具 CallToolResult，包括 content、structuredContent、isError isError 与实际字段，不要只读第一条文本就宣布成功

声明了 output schema 的工具可将结构化值交给脚本，包括携带结构化值的错误结果。校验失败、被拦截、无对应数据的执行异常等可以 reject。MCP 保留完整结果对象，因此 isError 必须显式检查。实际以发现返回的声明和该工具契约为准。S10、S14、S16

const result = await tools.bash({ command: "npm test" });
if (result.exit_code !== 0) {
  text({ passed: false, tail: result.output.slice(-4000) });
} else {
  text({ passed: true });
}

对 MCP，下面仅表达检查方式，工具名和参数都是教学占位，需先用发现接口确认：

// 伪代码：先发现真实工具，不要原样运行。
const result = await tools.mcp__docs__search({ query: "session" });
if (result.isError) throw new Error(JSON.stringify(result.content));
text(result.structuredContent ?? result.content);

两个层次的成功

Promise.allSettled() 的 fulfilled 只说明 Promise 没有 reject，不说明 shell 退出码为零，更不说明业务成功。可靠脚本先检查 Promise 状态，再检查结果中的错误标志或退出码。

同样，独立沙箱 sandbox.execute() 对脚本错误通常返回 { ok: false, error }，而不是按脚本错误直接 reject。脚本、宿主调用和模型 API 是不同层次，不共享一套错误表示。

await 是生命周期的一部分

// 错误示例：脚本可能先结束，未完成调用会被取消。
tools.read({ path: "package.json" });
return "完成";

// 正确示例：确认依赖工作已完成。
const source = await tools.read({ path: "package.json" });
text(JSON.parse(source).name);

脚本结束时，尚未结束的调用会请求取消；已经完成的外部副作用不会回滚。Promise.all() 因一个失败提前 reject，也可能让外层脚本结束，继而取消仍在进行的其他调用。独立读取适合 allSettled()；有依赖的操作按顺序执行。

store 不是数据库事务

store(key, value) / load(key) 保存小型 JSON 状态。CLI 只有脚本成功后，才把变更追加为 codemode-store 自定义会话条目；恢复和树形分支都只重放当前路径上的状态。单值 JSON 长度上限为 262,144 字符，总量为 1,048,576 字符。S10、S14

const count = (load("inspected") ?? 0) + 1;
store("inspected", count);
text({ count });

如果后面 throw，状态写入不提交；但之前通过 write 修改的文件依旧可能已经变更。所以“失败不提交 store”绝不等于“失败回滚整个脚本”。同样，在分支 A 保存的游标不会自动出现在从早先节点分出的 B，但文件系统仍是共享现实。

适合存：查询游标、选中的 ID、短摘要。不要存大型日志、图片 base64、完整仓库文件；大数据应由文件或外部服务承载。

取消不代表 worker 已经退出

CLI 当前最多允许同一 Pi 进程中两个 Code Mode worker 存活。Bun 下，某些不轮询中断的内建操作可能在返回取消结果后继续运行，直到该操作结束。v1.3.0 的修复把“对用户立即返回取消”和“实际 worker 退出后释放名额”拆开，避免重复取消积累残留 worker。S2、S13、S14

这个区别很通用：响应完成、任务停止、资源回收完成，是三个不同时间点。 不能在 timeout 返回的瞬间就把并发名额无条件释放。

四类常见错误的处置

症状 先检查什么 合理恢复
tools.X 不存在 拼写、标识符规范、工具是否可达 重新发现并描述工具，不反复猜名字
JSON.parse 失败 是否读到截断输出、日志或错误页面 换结构化工具或缩小读取内容
worker limit reached 是否还有运行或退出中的 worker 等已有 worker 退出，不做高频重试
超时或部分成功 哪些调用已产生副作用 查明实际状态，再决定是否重试；写操作需幂等策略

第 9 章：扩展、模型与界面，哪些没被 Code Mode 替代

本章目标：知道新增功能应该放在哪一层。

Code Mode 不负责所有定制。它负责模型生成的短程序编排，扩展负责安装到 harness 的可执行行为，skill 负责按需指令，提示模板负责复用输入，主题负责配色。这些能力互补。

扩展：从分散机制到一个入口

v0.35.0 把 hooks 与自定义工具统一成 extensions，并把文件式 slash commands 改称 prompt templates，避免和真正注册的命令混淆。当前 TypeScript 扩展工厂接收 ExtensionAPI，可以注册工具、命令、事件处理器、模型提供商、渲染器等。S2、S15

最小例子：

import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerCommand("hello", {
    description: "显示问候",
    handler: async (name, ctx) => {
      ctx.ui.notify(`你好，${name || "世界"}`, "info");
    },
  });
}

扩展直接运行在 Pi 进程中，能够接触文件、凭据与会话，不受 QuickJS 脚本那组全局变量限制。加载不可信扩展，比阅读一份不可信文档具有更直接的执行风险。

生命周期与状态放置

扩展工厂负责注册，不宜直接启动 watcher、socket、定时器。因为有些命令只加载扩展，并不启动会话。长寿命资源应在 session_start 或实际需要时开启，并在 session_shutdown 幂等清理。

分支相关工具状态可以放工具结果 details；不进入模型的持久数据用 appendEntry()；希望进入模型的自定义内容用 sendMessage()；跨会话数据用外部存储。重建状态应读取 getBranch()，不是遍历整个文件把其他分支也合并。S15

Provider 仍然承担协议适配

Code Mode 不会消除 Anthropic、OpenAI、Google 等协议差异。ai 层继续负责模型接入、流式归一化与内容转换。v1.3.0 切换模型时会丢弃由另一模型产生的历史 thinking 块，避免当普通文本交给新模型；特定提供商的缓存保持也是 provider 相关行为，不能推导成“所有模型切换都无代价”。S2

脚本中的 models.* 可访问模型目录、运行分类器、生成图片，但不能把聊天模型当作任意子 Agent 在脚本中调用。分类和生成图片可能计费，其 usage 会纳入会话成本；要检查 stopReason 与 errorMessage。图片要用 image(block) 展示，不要用 text() 打印 base64。S10

选择哪种集成方式

需要 优先接口 注意事项
人在终端中交互 TUI v1.0.0 起默认全屏，可切回 regular
一次性自动化 --print 一次运行后退出
消费事件流 --mode json stdout 为 JSONL 协议
非 TypeScript 宿主长期控制 RPC stdin 命令，stdout 响应和事件
Node/Bun 应用内嵌 SDK 宿主负责生命周期、资源和事件绑定
只想执行受限工具脚本 独立 pi-codemode 不必引入整个编码代理
需要持久任务恢复 实验性 pi-durable 独立 API、存储与重放策略

TUI 是事件消费者和交互层，不是业务循环本身。RPC 与 SDK 不需要复制一套“自己的 Agent 算法”；它们驱动同样的 session/agent 机制。自定义 UI 要区分 ctx.hasUI 与终端专属组件，不能假定 print 模式也有确认框。S7、S9、S15

SDK 的一个关键差异

CLI 会加载内置 Code Mode、tool-search、MCP 扩展；SDK 默认不会替你装好这三者。需要通过 DefaultResourceLoader.extensionFactories 添加，并在建立会话后 bindExtensions()，让 session_start 触发 MCP 后台连接。本书 examples/sdk-codemode-mcp.ts 保存了该版本官方示例。S20

设计练习： “每次调用 shell 前做企业策略校验”应该写进临时 Code Mode 脚本吗？不应该。应在工具边界实现可审计的扩展策略，并用 OS/容器限制补上真正的权限边界。模型生成的代码不是强制执行安全策略的地方。

第 10 章：从 0.99.2 到 1.3.0，具体差了什么

本章目标：避免把长期演进和最近两周的变化混在一起。

如果你的“0.9.xxx”其实是 0.99.2，前面很多机制你已经有了：Code Mode、独立 pi-codemode 包、工具发现、MCP、树形会话、统一扩展，并不是升级到 1.3.0 才第一次出现。下面只看这个较短区间。S2、S21

版本 Code Mode 及相关架构变化 对使用者的影响
1.0.0 缩短模型可见说明，增加错误恢复提示；加入 models.generateImages() 工具脚本提示更小，可以生成图像；探测工具是否存在要用 in
1.0.0 从 pi-agent-core 移除实验性 AgentHarness 与相关导出 依赖旧实验 API 的 SDK 使用者必须迁移，普通 CLI 不因此换内核
1.0.1 输出硬上限，防无限 text() 撑爆宿主；MCP 项目覆盖等 输出也受资源治理，不能只关心 VM 内存
1.0.3 image() 同时保存临时图片文件 后续回合可复制和引用图片路径
1.0.4 内建对象冻结；读图返回图片块；MCP 工具过滤规则修复 不可依赖修改 Array 等原型；图片可从 read 传给 image

1.2.0 声明显示 schema 约束；reachesTools、命名空间 aliases；MCP 解耦 工具编排器可替换，不必绑定特定内置实现
1.2.0 远程/inline 沙箱、portable 入口、确定性 sandbox.start() 独立包可部署到 Cloudflare，给持久重放提供基础

1.3.0 取消结果不等待实际退出；按真实 worker 生命周期限制容量 timeout 更及时，重复取消不会无上限积累 worker

“约少 40% token”到底指什么

v1.0.0 变更日志给出的例子是：默认工具并启用 Code Mode 时，一个 GPT-5.6 请求的提示规模从约 5,300 降到约 3,300 token。减少来自说明精简、按需阅读模型 API 文档、避免重复声明等。它是上游记录中的特定场景，不是本书实测，更不是任何项目、模型、工具数量下都少 40%。S2

三个明确的迁移断点

探测工具存在性。 新版访问未知成员可能抛出带近似匹配建议的错误。旧代码 typeof tools.someName 也可能触发属性读取，改用 "someName" in tools。S21

MCP 类型声明。 独立包在 v1.2.0 移除了 MCP_TYPESCRIPT_PREAMBLE 和 mcpStructuredContentSchema()。输出 schema 直接描述完整返回对象，声明渲染不再依赖一个悬空的 CallToolResult<T> 名称。消费这些底层导出的应用要更新。S21

独立沙箱 close()。 v1.3.0 中结果和 close() 在请求关闭后即可 settle，不代表 worker 已退出。自己管理资源池时，用 onWorkerStarted(exited) 或 acquireWorker() 的释放回调追踪真实退出，不能照旧按结果完成释放容量。S13、S21

不要继续照旧实验目录做设计

v1.0.0 的 pi-agent-core 清理与 v1.2.0 的 CLI 实验栈清理是两件事。前者确实移除了该包的旧实验性 harness 导出；后者移除的 client/protocol/server 栈未进入正式 coding-agent 发布包。做源码研究时能看见它们，不能据此假设它们都是稳定产品 API。S18、S22

第 11 章：独立沙箱、云端执行与 Durable 重放

本章目标：分清三个看似相近、恢复保证完全不同的架构。

“Code Mode 可以恢复”这句话缺少主语。普通 CLI、独立沙箱库、Durable 扩展提供的保证并不相同。

形态 谁拥有工具与状态 中途崩溃后怎样处理
普通 CLI Code Mode AgentSession 与扩展 已成功提交的小型 store 可恢复；没有普通脚本指令级自动续跑保证
独立 CodemodeSandbox.execute() 你的宿主 你自己管理持久化；一次执行不自动变持久任务
sandbox.start() 宿主驱动的确定性 VM 提供可重放机制，宿主仍需日志与调度
实验性 pi-durable/codemode Durable Harness、存储、任务与 journal 重启后重放已记录结果并继续；未完成外部调用服从各自 replay 策略

11.1 不用整个 Pi，也能用沙箱

独立 pi-codemode 的核心接口是注入工具、执行脚本、读取结构化执行结果。工具函数在宿主执行，VM 只保留受限 JavaScript 环境。S13

import { CodemodeSandbox } from "@earendil-works/pi-codemode";

const sandbox = new CodemodeSandbox({
  timeoutMs: 10_000,
  tools: [{
    name: "lookup",
    execute: async ({ id }) => ({ id, title: `条目 ${id}`, privateNote: "不输出" }),
  }],
});

try {
  const result = await sandbox.execute(`
    const row = await tools.lookup({ id: 7 });
    text({ id: row.id, title: row.title });
  `);
  if (!result.ok) throw new Error(result.error.message);
  console.log(result.output);
} finally {
  await sandbox.close();
}

这是独立库示例，直接注入自己的可信函数。若要套进现有 Agent，不能因为省事直接调用原始 tool.execute()，把既有验证和钩子绕过。官方 CLI 走 ctx.executeTool()；低层 Agent 应使用相应工具调用管线。S13

11.2 为什么 Cloudflare 要把 VM 放进另一个 Worker

Node/Bun 用 worker thread 把计算隔离出主线程。Cloudflare 没有同样的 Node worker 环境，且 QuickJS 同步计算会阻塞承载它的 isolate。

v1.2.0 新增 RemoteCodemodeSandbox：工具和调用记录留在会话一侧，VM 放到单独部署的 Worker 中的 Durable Object，每次工具调用通过 Workers RPC 回到宿主。这里的 Durable Object 是 Cloudflare 基础设施，不等于 pi-durable 包。S13、S21

上游 README 记录了特定 Cloudflare 测试：让脚本持续计算十秒，放在会话对象内或由它加载的 Dynamic Worker 会延迟其他会话请求约十秒，单独部署的 Worker 则约为 50 ms。该数字是上游环境测量，用来说明部署边界选择，不承诺本地环境或你的账号相同。

Cloudflare 还有两个限制要单独理解：计算不 yield 时墙钟 timeout 不足以约束 CPU，使用 interrupt budget；远程 abort 可以先结束调用侧等待，VM 在下一次工具调用或耗尽预算时才停。远程默认每 VM 32 MiB，不能套用普通 CLI 的 256 MiB。

InlineCodemodeSandbox 直接在调用线程运行，适合能接受阻塞的宿主。portable 入口不包含 Node imports，方便这些环境共用同一脚本 API。

11.3 Durable 恢复的是执行历史，不是 VM 内存快照

pi-durable 在 v0.99.2 的仓库中已经存在，最新区间新增的是与确定性脚本重放结合的 Code Mode 等能力。它是实验 API，版本间可随时变化。Harness 把会话条目、文档状态、任务和提交放进存储，提交后才发布相关状态；持久任务保存阶段检查点，重启后继续调度。S23

运行脚本时：

  1. 固定虚拟时钟、随机种子、时区和 VM 指纹等条件。
  2. 脚本发出嵌套工具调用，工具本身成为 Durable 任务。
  3. 宿主在把结果交给 VM 之前，将结果与顺序写入 journal。
  4. 进程崩溃后重新运行脚本，按原来顺序喂入记录的结果。
  5. 脚本因此发出相同调用，按 key 重新关联已完成或仍在运行的任务，再继续新的工作。

sandbox.start() 的确定性约束包括：Date.now() 来自宿主提供的时间、随机性来自 seed、固定 UTC、不暴露 WeakRef/FinalizationRegistry、结果按宿主编号应用。它不要求保存整个 QuickJS 堆快照。S13、S23

一个“扣款后崩溃”的边界案例

假设工具向外部系统发起扣款，外部扣款成功，但本地还没记录结果就崩溃。重启后能否再次调用？不能靠“脚本可以重放”来决定。Durable 工具只有声明 replay: "safe" 才能在中断后重新执行；否则会产生 interrupted 错误。即便声明 safe，外部副作用仍需服务端幂等 key 或查询确认。S23

所以它并不提供跨任意外部服务的“恰好一次副作用”魔法。它提供的是可记录、可检查、可恢复的调度和调用关系。代码路径改变、VM 指纹或 Code Mode 版本变化，以及 deadline 已经过期，都可能令重放报错，而不是盲目继续。

11.4 远程执行环境解决另一个问题

pi-env 把 Durable 工具的文件与命令操作转到远端机器：本地保留 Harness、存储和凭据；通过 SSH 启动小型 Rust daemon，运行协议化文件与进程操作。RemoteExecutionEnv 尽量保持与 NodeExecutionEnv 相同的语义。S24

这与把 QuickJS VM 放远端是两个独立选择：VM 放哪里，决定脚本计算在哪里；执行环境放哪里，决定文件和命令在哪里发生。远程执行也不自动成为沙箱，仍要限制远端账户权限、网络和可用凭据，核验 SSH host key。

这张图与第 3 章的 CLI 依赖图应分开阅读：一个是实验性持久执行方案，一个是普通编码代理。它们复用模型和沙箱基础库，不意味着生命周期、状态格式和恢复契约相同。

五个问题，检查是否真的理解

  1. Code Mode 是否等于多个工具并行？ 不等于。新版普通调用也能并行；Code Mode 多了程序控制流和中间结果筛选。
  2. 脚本失败，之前写文件会撤销吗？ 不会。成功才提交的小 store 与外部文件写入没有统一事务。
  3. MCP Promise fulfilled 是否意味着成功？ 不意味着。还要检查 isError。
  4. 普通 CLI 恢复会话是否会从脚本中断的语句继续？ 没有这个通用保证。Durable Code Mode 通过日志和确定性重放提供另一种恢复机制。
  5. QuickJS 没有文件系统，shell 就安全吗？ 不能这样推断。注入工具背后的权限才决定影响范围。
